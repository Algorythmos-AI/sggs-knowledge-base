# Harnesses and golden vectors

Two kinds of proof guard the engines. **Harnesses** measure how well search serves real seeker
behaviour, so a change can be judged corpus-wide rather than on a few examples. **Golden vectors**
record exact outputs, so no change to the fold, the waterfall or the verifier can ship unnoticed —
here, over HTTP against every deploy, or in the app's Swift port.

## The harnesses

| Harness | What it types | What it measures | Run |
|---|---|---|---|
| `tools/roundtrip_harness.py` | every corpus line's *own* transliteration (or a sample, an Ang range, a word cap) | does the line come back at rank 1 / in the top 3 — the "does every line resolve when a user types it" metric; failures bucketed by form and Ang range | `python3 tools/roundtrip_harness.py [--sample N]` |
| `tools/casual_quote_harness.py` | the first ~6 words of a real line, **casualised**: modern postpositions (`kai → ka`, `kee → ki`), dropped aspirates (`khelio → kelio`), shortened vowels (`kool → kul`) | top-1 / top-3 recall for the way seekers half-remember a verse (the class that produced the *jamuna ka kul khel kelio* bug) | `python3 tools/casual_quote_harness.py [--sample N]` |
| `tools/chaos_harness.py` | attack files: `{agent, behavior, query, canonical_translit, canonical_ang}` | PASS iff a top-3 result is the canonical line (transliteration match, Ang ± 1), against a **running** server | `python3 tools/chaos_harness.py "qa/chaos/attacks_*.jsonl" qa/results/chaos.jsonl` |

The first two run `do_search` in-process and write per-line JSONL under `qa/results/`;
`make harnesses` runs both. Re-run them before and after any change to a tier, a weight or the
fold, and compare the summaries: the waterfall is tuned corpus-wide, and a local improvement
often costs recall elsewhere.

## The golden contract

`tools/gen_golden_vectors.py` drives the **real** functions — `roman_norm`, `difflib`, `do_search`,
`verify`, the reader, timing, banis, analytics — and records their exact outputs under
`contract/`. The files and their record counts, from `contract/_meta.json`:

<!-- sggs:code file="contract/_meta.json" lines="1-20" -->
Source: [`contract/_meta.json`](../../contract/_meta.json) — the counts and the database the vectors were built against.

| File | Pins |
|---|---|
| `golden_roman_norm.ndjson` | the fold: 24,719 input → output pairs ([The Roman fold](the-roman-fold.md)) |
| `golden_difflib.ndjson` | `SequenceMatcher.ratio()` values, repr-exact, so the port's scorer equals Python's |
| `golden_search.ndjson` | real queries through the waterfall and their results |
| `golden_verify.ndjson` | claims and their full verdicts ([Verification engine](verification-engine.md)) |
| `golden_reader.ndjson` | Ang, shabad and Hukam projections |
| `golden_timing.ndjson`, `golden_banis.ndjson`, `golden_analytics.ndjson` | the knowledge, Nitnem and insight layers |
| `golden_pahar.ndjson` | the pahar clock (generated by `frontend/scripts/gen-pahar-vectors.mjs`) |
| `openapi.json` | the API's shape, inferred from real responses ([Contract and OpenAPI](../api/contract-and-openapi.md)) |

`_meta.json` also records the `db_sha256` the vectors were generated from; the
`scripture-integrity` workflow requires it to equal the [dataset pin](../data/dataset-pin.md).

## Where the contract is enforced

| Where | How |
|---|---|
| this repository, every PR | `make contract`: regenerate and `git diff --exit-code contract/*.ndjson` — any drift must be a deliberate, reviewed regeneration |
| every deploy (staging and production), the API image | `tools/contract_http.py --base <origin>` replays the same projections over HTTP and compares by parsed-JSON equality |
| through the staging gateway | the whole contract passes through `sggs-staging.vercel.app`, proving the split services answer exactly like the monolith |
| production, every 6 hours | the data canary replays the contract against production |
| gurbani-soul-ios | `vendor.lock.json` pins every contract file by sha256 at a platform release; byte-parity tests hold the Swift port to them |

A change to the engines therefore has one honest path: change the code, re-run the harnesses,
regenerate the contract, review the diff, release, and let the app re-vendor at the new tag.
